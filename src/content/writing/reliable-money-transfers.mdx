A money transfer is not reliable simply because an API returns a successful status code. The system must preserve the meaning of the operation when clients retry requests, connections fail, or multiple transactions overlap.

For financial software, correctness is a property of the operation and its persisted state—not just its HTTP response.

## Start with an invariant

Imagine transferring KSh 500 from account A to account B, with both accounts maintained in the same relational database.

The operation must preserve several rules:

- Account A is debited by KSh 500.
- Account B is credited by KSh 500.
- Both changes succeed together or neither change takes effect.
- The same logical transfer is not applied twice because of a retry.
- The source account cannot spend more money than the business rules permit.

These rules are invariants: conditions that must remain true regardless of how requests arrive or fail.

They should influence the data model, transaction boundary, database constraints, and tests from the beginning.

## The ambiguous outcome problem

Consider this sequence:

1. A client submits a transfer request.
2. The server processes and commits the transfer.
3. The network connection fails before the response reaches the client.
4. The client cannot tell whether the transfer succeeded.

The client has an ambiguous outcome. Sending a completely new operation could transfer the money twice.

This is where idempotency becomes useful.

An idempotency key identifies a logical operation across retries. The server associates the key with the operation and its outcome, enforcing the relevant uniqueness rule in persistent storage.

A robust design must answer more than whether a request contains a key:

- **Same key, same request:** return the original outcome or safely recover it.
- **Same key, different request:** reject the conflicting reuse.
- **Same key submitted concurrently:** ensure only one logical operation is applied.
- **Failure before commit:** allow a safe retry according to the transaction and idempotency design.
- **Failure after commit:** make it possible to recover the committed result without applying the transfer again.

The key alone does not provide these guarantees. The persistence model, transaction boundaries, and retry behaviour must work together.

## Keep related financial changes atomic

When both accounts belong to the same relational database, the debit, credit, and transfer record generally belong in one database transaction.

An illustrative example is:

```python
async with session.begin():
    await debit_source_account(...)
    await credit_destination_account(...)
    await record_transfer(...)
```

This is illustrative pseudocode, not a complete production implementation. It omits the details of balance validation, concurrency control, idempotency persistence, and error handling.

The transaction ensures that the related database changes commit together or roll back together. It does not automatically prevent every race condition.

For example, two concurrent transfers might both read the same available balance. If neither operation protects the balance check and update, they could both make a decision using stale state.

Possible protections include conditional updates, row-level locking, or transaction isolation strategies appropriate to the invariant. The correct choice depends on the schema and database behaviour.

## Keep the source of truth explicit

A financial backend needs a clear answer to one question: which component is authoritative for the financial state?

If PostgreSQL owns the financial records and balances, a Redis cache should not independently become the authority for whether a transfer has occurred.

Caching, rate limiting, sessions, and idempotency coordination can serve useful purposes, but their roles must be explicit. Financial correctness should not depend on an unrelated cache remaining available or perfectly synchronized.

The same principle applies to asynchronous processing. A downstream event consumer should not be treated as proof that the original database transaction succeeded unless the event represents a committed outcome.

## Separate database commits from event delivery

Suppose a successful transfer must also produce an event for notifications, analytics, or another downstream process.

Committing the database transaction and publishing a message to Kafka are two separate operations. A database transaction does not automatically make a broker publish atomic with the database commit.

This creates a failure window: the database can commit while event delivery fails, or an event can be delivered while a later step fails.

A transactional outbox is one approach to managing this boundary. The application writes the business changes and an event record in the same database transaction. A separate publisher then delivers pending events to the message broker.

The publisher and consumers still need retry and duplicate-handling strategies. Outbox delivery is generally designed around reliable repeated delivery, not an assumption that every message is delivered exactly once across all systems.

This distinction matters when describing an architecture: designing an outbox-based flow is not the same as having a fully deployed and operational event pipeline.

## Test failure paths deliberately

Happy-path tests establish that an ordinary request works. They do not establish that the operation remains correct when something goes wrong.

Useful tests include:

1. Submit the same idempotency key twice and verify that the logical transfer is applied only once.
2. Reuse a key with different request data and verify the defined conflict behaviour.
3. Attempt a transfer when the source account has insufficient funds.
4. Execute competing transfers against the same balance.
5. Force a failure during the database transaction and verify that partial financial changes are not committed.
6. Simulate a lost client response after a successful commit and verify that a retry recovers the original outcome.
7. If an outbox is implemented, test event recovery and duplicate delivery separately.

Concurrency tests should use independent transactions or sessions and verify the final persisted state, not just the status code returned by an API.

## The takeaway

Reliable money movement begins with explicit invariants. Database transactions protect related changes, idempotency controls retries, concurrency mechanisms protect shared state, and deliberate tests verify the resulting behaviour.

Additional infrastructure can help, but it cannot compensate for an undefined notion of correctness.

The important engineering question is not simply whether the transfer endpoint works. It is whether the operation remains correct when requests are repeated, transactions compete, and components fail.
